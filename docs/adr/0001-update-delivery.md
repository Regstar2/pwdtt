# ADR 0001: доставка обновлений PWDTT

- Статус: принято
- Связанная задача: #21

## Контекст

PWDTT распространяется как локальное desktop-приложение. Старый update checker обращался к release-каналу upstream `luminescq/PWDTT`, а версия приложения дублировалась вручную в исходном коде. Такой подход допускает рассинхронизацию между tag, опубликованным бинарником и версией, которую видит runtime.

Полный self-update также нельзя считать безопасным только на основании наличия download URL: перед автоматическим запуском скачанного исполняемого файла нужен проверяемый механизм целостности или подписи.

## Решение

1. Единственный release-источник поддерживаемого форка — GitHub Releases `Regstar2/PWDTT`.
2. Release build получает версию из Git tag `vX.Y.Z` через Go ldflags (`-X pwdtt/backend.Version=X.Y.Z`). В исходниках остаётся только явный fallback `dev`.
3. `dev` build не сравнивается с release semver и не показывает ложное предложение обновления.
4. Update checker использует GitHub endpoint `releases/latest`, то есть stable-канал. Ошибка сети или API не блокирует запуск приложения; frontend может повторить проверку позже.
5. Обновление считается доступным только если latest version новее текущей и в release есть официальный asset, совместимый с текущими `GOOS/GOARCH`.
6. Для Windows и Linux сейчас поддерживается только `amd64`. `amd64` asset никогда не подставляется для `arm64`. `PWDTT-macos.zip` считается universal asset, потому что release workflow собирает его через `darwin/universal`.
7. Текущий пользовательский flow: проверить версию → показать release notes → открыть официальный GitHub release asset в браузере. Приложение не заменяет и не запускает скачанный бинарник самостоятельно.
8. Release создаётся в том же GitHub Actions workflow, который собрал артефакты для tag. Это исключает публикацию артефакта от другого workflow run/commit.

## Почему пока без self-update

Текущий release pipeline не передаёт update checker проверяемую подпись или SHA-256 manifest для исполняемого файла. Автоматически скачивать и запускать бинарник без такой проверки противоречило бы требованиям безопасности механизма обновлений. Поэтому выбран безопасный fallback с переходом к официальному GitHub Releases.

К полноценному self-update можно вернуться после появления подписанного release pipeline или опубликованного checksum manifest и проверки целостности перед запуском установщика/заменой бинарника.

## Последствия

- tag является каноническим источником release version;
- локальные сборки без ldflags явно отображаются как `dev build`;
- отсутствие подходящего asset не маскируется под доступное обновление;
- GitHub API остаётся внешней необязательной зависимостью и его недоступность не ломает основной сценарий PWDTT.
